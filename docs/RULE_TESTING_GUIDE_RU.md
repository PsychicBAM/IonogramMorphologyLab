# Руководство по тестированию правил — 1.1.1

**Rule Testing Lab** оценивает **поведение реализации** правила и метрики на размеченной dev-выборке. Успешный прогон лаборатории **не** является независимой научной валидацией.

## Перед тестом

Подготовьте набор с документированными:

- источником данных и разрешениями на использование;
- определениями классов и протоколом разметки;
- покрытием профиля прибора;
- рецензентами и временным диапазоном;
- известными ambiguous и negative случаями.

Не подбирайте пороги на слепых evaluation-данных, если протокол это явно не разрешает.

## Порядок работы

1. **Выбор версии правила** — ID, статус, версия YAML в проекте или библиотеке.
2. **Размеченный набор** — CSV или кадры проекта с expert labels.
3. **Метод split** зафиксируйте **до** просмотра метрик (например, по блокам дат — без утечки соседних кадров между train/test).
4. **Метрики** по целевой оси: одной accuracy недостаточно при abstention; смотрите confusion matrix и ошибки по подгруппам.
5. **Threshold sweep** — по желанию; рабочую точку документируйте отдельно от exploratory прогонов.
6. **Run test** — разберите FP, FN и abstained/indeterminate в **Viewer**.
7. **Экспорт прогона** — fingerprint набора, split, версия правила, настройки, абзац ограничений.

## Интерпретация

| Наблюдение | Действие |
|------------|----------|
| Много FP на ambiguous O/X | Исключения или abstention; не включать strict без доработки |
| Часто нет признаков | Профиль или registry признаков |
| Хорошие метрики только на synthetic | Повторите на dev-выборке станции |
| Один файл в train и test | Невалидная валидация — пересмотрите split |

## Режим scientific strict

При strict фильтрации в batch участвуют только approved/verified статусы. Завершите записи Rule Testing Lab до повышения статуса.

## Безопасность и данные

- Импорт pack — только из доверенных ZIP ([THREAT_MODEL.md](THREAT_MODEL.md)).
- Редактируйте локальные пути в отчётах перед публикацией.
- Не прикладывайте ограниченные ионограммы к публичным issues.

## Публикации

Укажите:

- rule ID и хеш версии;
- provenance меток и согласие рецензентов (если есть);
- дизайн split и исключённые эпохи;
- долю abstention и режимы отказа;
- явную формулировку: результаты — **development evidence**, не мультистанционная валидация.
